# Exceptional implementation phases

Load this reference only when Planner proposes phases or an approved phased plan is active. Ordinary Markdown task groups use one Coder assignment and no intermediate gates.

The normal path is one Coder assignment across Markdown checkpoint groups. Only exceptionally large features use Planner's ordered `implementation_phases: [{id, title, task_ids}]`; otherwise omit implementation_phases (an empty array is also unphased). At least two phases partition all actual tasks exactly once in approved execution order. Stable phase identities cannot renumber/reuse completed work. The final phase includes integration, final Test-Maintenance and Verification. The tasks approval and consolidated Planner output establish the plan; phases create no additional approval gate or progress document.

Every subsequent Planner return retains the phase plan associated with the current tasks content unless it records a tasks content revision. Changing phase identities, order or task ownership, including adding or removing phases, is a material tasks revision and requires the applicable tasks approval before review readiness. A title-only editorial correction follows the existing version and approval-basis rules. Consolidation cannot replace the approved plan by changing only the wrapper.

A revised approved plan may change unfinished phase work. Preserve completed phase IDs/order/task ownership and their historical plan references. After the required spec acceptance and coding authority, record `coding-started` against the new plan to rebind an unfinished assignment, reusing its native Coder context where available and retaining its repair counts/evidence. This is an authorized scope revision, not an interruption retry or permission to restart the same plan. Prior completed-stage evidence still needs its normal applicability check before advancement.

Coding/review starts and outputs use `work_scope: {kind: feature}` or `{kind: phase, phase_id: P1, plan_ref: {event_id, kind: spec_change_wrapper}}`. An absent scope reads as feature only; no implicit phase authority. Nonfinal completion records `coding-phase-complete` with a cumulative scoped wrapper and stays `coding_in_progress`. Intermediate review uses existing review events and returns to `coding_in_progress` on success. Findings use existing code findings states and scoped repair starts. Next approved phases use `coding-started` and a fresh Coder context. The last Coder returns whole-feature `coding-complete` directly into final review, with no extra intermediate review. Only whole-feature review establishes `code_approved`.

Repair starts must cite the latest review in the active scope and address its unresolved findings. Final-review repairs retain whole-feature scope and the last Coder's responsibility; an earlier phase review cannot authorize them. A catch-up review that finds problems in an earlier phase makes that phase the active repair scope, preserving its own allowance and the later assignment for recovery.

| Feature assurance | Nonfinal review | Repair cycles per nonfinal stage | Final review / allowance |
| --- | --- | --- | --- |
| Basic | None | None | Basic / one |
| Standard | Basic | One | Standard / two |
| Maximum | Standard | Two | Maximum / existing rigorous loop and stall safeguards |

Counts include completed repair/re-review pairs only, separately for spec, each nonfinal phase and final implementation. They survive reassignment, interruptions, settings changes and returning to unresolved work. Additional-cycle authorizations use `limits.phase: spec`, `code`, or `phase:P1` and reference that stage's review. Acceptance within allowance does not cause an unnecessary limit prompt. Initial phase review covers the entire delivered scope and relevant dependencies, not future tasks. First final review is an initial whole-feature review, informed by prior phase reports/evidence. Preserve all unresolved findings with stage provenance into final acceptance; policy-based intermediate dispositions are evaluated under final assurance, while actual user decisions and revisit conditions remain authoritative.

When an intermediate review is required, feature capability includes `stage_assignments.intermediate_reviewer`, using the full Reviewer model and effort mapping `max → high`, `xhigh → medium`, `high → low`. Repository defaults are unchanged. Present this with the phased tasks plan and record acceptance through a complete capability override alongside existing approval. Basic phases may omit it; if assurance later requires an intermediate review, resolve it before dispatch. Absence grants no assignment. Unmapped/unsupported settings require the existing explicit limitation/choice process, with no invented effort minimum or fallback. Later phased Reviewer changes replace complete capability to keep full/intermediate assignments consistent. Final review uses `roles.reviewer`.

The last Coder owns cumulative integration and all final-review repairs, including earlier-phase work. Helpers only explore/run tests using the accepted helper assignment and report concise evidence; Coder intentionally edits and interprets results. Read-only resume results expose derived scope, readiness, scoped counters and evidence gaps; no second persisted state registry is introduced.
